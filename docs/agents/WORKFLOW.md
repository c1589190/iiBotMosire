# 工作流维护手册

> **本文件属于项目维护。** 项目目标运行序列、事件/载荷、状态机与验收判据按
> `docs/superpowers/specs/**` 执行；本文只规定工作方式。

## 一、控制方、责任区与 Agent

- **控制方**：调查综合、约束设计、派单、审阅、验收与提交；默认不亲自写生产代码。
- **调查 Agent**：只读；任务书给方向与问题清单，不允许无方向扫全项目。
- **办事 Agent**：一个责任区一个写代码 Agent；到编译通过为止，不擅自改测试、不跑全量门禁、不 commit。
- **测试 Agent**：生产代码落地后按验收判据写测试；必须覆盖负向用例与状态机非法转移。
- **责任区**：一个可独立编译、可独立验收的目标/问题域，不按文件数量或计划编号切。
- 同一时刻只允许一个写代码 Agent；只读调查可并行，但不得共享写目标。
- worktree 统一放 `<仓库根>/worktree/<name>/`。

## 二、派单前必须有的设计

凡涉及以下任一项，必须先落设计文档，再派实现：

- 持久状态组件、事件类型、回放规则、快照与迁移；
- 运行阶段、回合状态机、自动结算、定时器；
- 对外 API / MCP 工具面 / QQ 命令 / 事件载荷；
- 数据所有权、可见性过滤、提示词组合、工具权限；
- 外发消息幂等、重试、超时与人工干预路径；
- 数值公式或随机规则。

设计文档至少写：

1. 需求来源与用户原话；
2. 目标/非目标；
3. 现状事实（`file:line` 或 URL）；
4. **目标运行序列**（阶段、顺序、读写、所有权、失败、日志、测试锚点）；
5. 接口、载荷、数据流与存储语义；
6. 不变量与失败语义；
7. 验收判据 + 负向用例；
8. 文件所有权与停止条件。

**派单书自包含**：引用设计路径 + 小节号，并复述关键形状。子 Agent 发现设计与用户原话/红线冲突时立即上报。

## 三、测试与验收节奏

- 写代码责任区先做到编译通过；编译通过不是验收。
- 测试按验收判据而不是按实现反推；关键不变量做变异自证。
- 回合状态机、事件回放、可见性、幂等、外部 MCP 授权面必须有负向用例。
- 真实 NapCat/LLM/MCP 联调与长跑不进普通 JUnit 门禁；用独立脚本/隔离数据目录，见 `VERIFICATION.md`。
- 没跑过的命令标 `NOT_RUN`；证据不足标 `EVIDENCE_INCOMPLETE`。

## 四、评审与停止条件

- 评审按风险触发：权限/可见性、进程线程生命周期、持久事件/事务、跨模块契约、外部 MCP 写面。
- 单模块评审不超过 3 轮；小改动控制方读 diff 即评审。
- 做不到验收判据 = **BLOCKED，不是 DONE**；“写进风险文档”不能替代判据通过。
- 纯实现困难给 fail-closed 方案并保持 BLOCKED；只有设计冲突/需用户裁定才停手等指令。
- 发现文档与代码不一致：先回代码/实际运行核，再判定文档错、实现错还是夹具错。

## 五、开发中期文档动作

每完成一个责任区、门禁、交接或上下文压缩前：

1. 更新 `docs/agents/STATUS.md`（目标、HEAD/dirty、门禁、未验证、下一步）；
2. 需要长文时写 `docs/superpowers/status/YYYY-MM-DD-*.md`，文件头标历史快照；
3. 新设计裁定进 `specs/**`；维护裁定进 `MAINTENANCE_RULINGS.md`；
4. 真实 RED 证实的复用判断流程才登记 Skill 候选；
5. 不把聊天记录当作唯一留痕。

## 六、提交与协作

- 不 `git add -A`；按关注点分批提交，提交前看 `git status` 与 staged diff。
- 不擅自 commit/push；用户当次指令优先。
- 提交信息中文，写清改动、原因、实际验证数字与未验证项。
- 不提交运行时数据、数据库、token、日志和 `target/`。
- 不篡改历史文档；更正用状态头/追加说明。

## 七、用户协同门（M-004）

- 需要真实 QQ 操作、真实外部确认、凭据、人工观察或其他必须由用户完成的状态时，**先停下**。
- 停下时只给：已确认事实、当前风险、用户本轮需要做的一件具体事、回复后我会做什么。
- 等待用户回应，不把等待写成自动继续；不连续自发外发、不用自测消息冒充 Bot/秘书/玩家回复。
- 真实外发前说明目标账号/群和目的；没有明确授权不发送测试消息。
- 无法继续时标 `WAITING_USER` 或 `BLOCKED`，不写 DONE。
