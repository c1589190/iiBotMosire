## 1. 目标运行序列

### 1.1 私信即时送达提示

```text
QQ inbound(message_id)
→ adapter 去重
→ dispatcher dedupeKey 防重
→ 若为已登记玩家的私聊：
     立即发送 ACK（独立幂等键，不经过 LLM）
→ 进入该玩家 mailbox
→ 秘书 Agent 构建/调用工具/生成正式回复
→ 正式回复进入 outbox
```

- ACK 是“已收到，正在处理”的状态提示，不是 Agent 回复，也不进入 LLM 上下文。
- 同一 `dedupeKey` 的 ACK 只发送一次；发送失败/UNKNOWN 只记录，不阻塞主处理。
- `/确认` 等命令也先 ACK，再由宿主确定性处理。
- 未登记 QQ、群聊、自身消息不发送 ACK。
- ACK 使用独立幂等键：`ack:<dedupeKey>`。

### 1.2 秘书独立工作区

每个玩家一个逻辑工作区：

```text
dataDir/secretaries/<playerId>/
  public/       公共资料与已发布公共推文（只读）
  player/       该玩家可见资料、自己的 brief、私密推文（按可见性）
  gm/           GM 下发给该秘书的资料（可读）
  notes/        秘书自己的整理笔记（可写）
```

- 实现基于 `workspace-mosire` + `docs-mosire`，不直接拼绝对路径。
- 秘书 Agent 工具面：
  - `secretary_workspace_list/read/search`（只读；路径经权限解析）；
  - `secretary_note_append`（只能写 `notes/`，破坏性/敏感标记）；
  - 不得读取其他玩家工作区、GM 私密草稿或未发布的他人私密推文。
- GM（DIRECTOR/GM/SUPERVISOR）工具面：
  - `gm_secretary_list`；
  - `gm_secretary_read` / `gm_secretary_dispatch`（下发资料到 `gm/` 或 `player/` 的受控路径）；
  - `gm_secretary_chat`：向某玩家秘书发送 GM 消息，秘书可在自己的上下文中回应；
  - GM 不应直接以玩家身份创建/确认决策。
- 所有工作区操作进入事件/审计；文件名与内容不得泄露 token、API key、其他玩家隐私。

### 1.3 权限与推文审核

推文状态机：

```text
DRAFT → PENDING_APPROVAL → APPROVED → PUBLISHED
                         └──────────→ REJECTED
```

- 公共推文：秘书只能**生成草稿**，不能直接发；GM/DIRECTOR/SUPERVISOR 审核并最终发送。
- 私人推文：秘书只能为自己所属玩家生成草稿；GM 审核并最终发送到该玩家私聊。
- 秘书可见：
  - 公共资料；
  - 已发布公共推文；
  - 自己所属玩家的可见资料/已发布私密推文；
  - 自己创建的草稿。
- 秘书不可见：
  - 其他玩家资料/私密推文；
  - GM 未批准的他人草稿；
  - 系统/进程/密钥工具。
- 玩家可见：自己的私密推文 + 已发布公共推文。
- GM 可见所有游戏资料、推文草稿与审核记录。
- 最终外部发送（QQ 公共群/私聊）只由 GM 通道执行；玩家秘书没有 QQ 发送工具。
- 现有中央推演结果 `publicNarrative` / `playerOutcomes` 由 GM 的 `tf_publish_turn` 触发发送，视为 GM 最终发布；秘书草稿走独立推文审核流程。

建议领域权限矩阵：

| 能力 | PLAYER | SECRETARY | DIRECTOR/GM | SUPERVISOR(MCP) |
|---|---|---|---|---|
| 读公共资料/已发布公共推文 | 是 | 是 | 是 | 是 |
| 读自己玩家资料/已发布私密推文 | 是 | 是 | 是 | 是 |
| 读其他玩家隐私 | 否 | 否 | 是 | 是（游戏控制面） |
| 创建公共推文草稿 | 否 | 是 | 是 | 是 |
| 创建自己玩家私密推文草稿 | 否 | 是 | 是 | 是 |
| 批准/拒绝推文 | 否 | 否 | 是 | 是 |
| 最终发送推文/公共叙事 | 否 | 否 | 是 | 是 |
| 管理秘书工作区 | 否 | 仅 own notes | 是 | 是 |
| 直接 QQ 发送工具 | 否 | 否 | 否（经宿主 outbox） | 否（只能通过领域发布命令） |

实现要求：

- 推文/资料过滤在进入秘书上下文之前完成；
- 发布命令使用 expectedRevision + idempotencyKey；
- 审批与发布事件可审计；
- 推文快照不进入事件 payload 全文，只存 hash/标识与必要摘要；正文由版本化存储/工作区保存。

### 1.4 多模型与 GM 推演秘书 Agent

模型路由改为命名注册：

```text
secretary   → 玩家秘书模型
adjudicator → 中央推演模型
gmAide      → 外部 GM 专用推演秘书模型
```

- `llm` 继续作为默认路由，向后兼容；新增可选 `llmRoutes` 覆盖具体路由。
- 每个 Agent 使用独立 route；最终配置必须可审计（只记录 route 名，不记录 key）。
- 允许通过本地配置切换模型；运行时热切换如实现，必须有显式 admin/supervisor 工具、审计与失败回退。
- `gmAide` Agent：
  - 独立上下文与模型；
  - 只读工具：全量世界事实、回合/决策/事件、秘书工作区、推文；
  - 无 QQ 发送、无 `doc_create`/`doc_edit`、无进程/密钥工具；
  - 只能把整理结果返回给 MCP/GM 调用者；
  - 不直接提交世界变更、不替玩家确认。

## 2. 模块与责任

| 层 | 责任 |
|---|---|
| `iibot-connect` | 外部 QQ 接入，不感知权限/推文/Agent |
| `iibot-connect-agent` | QQ 工具与 AgentLib 权限元数据 |
| `iibot-taskflow` | 送达事件语义、秘书工作区端口、推文状态机、权限矩阵、Agent 工具、GM 推演秘书 |
| `iibot-app` | 即时 ACK 调度、Workspace/Docs 装配、模型路由装配、MCP 控制面与最终发布 |
| `iibot-taskflow.control` / `app/mcp` | 仅暴露经过权限矩阵的游戏事件流工具 |

## 3. 实施顺序

1. v2-A：即时 ACK + 异步处理测试；
2. v2-B：秘书工作区与 GM 下发/读取/对话；
3. v2-C：权限矩阵与推文草稿/审核/发布；
4. v2-D：多模型路由与 GM 推演秘书 Agent；
5. v2-E：真实单人回归 + 多玩家/DSH/MCP 验证。

## 4. 不变量

1. 玩家身份只来自配置，秘书不能把自己变成 GM。
2. 秘书不能直接向 QQ 发推文或公共叙事。
3. 秘书上下文只能含其可见资料；过滤发生在模型调用前。
4. 推文审批/发布都有 expectedRevision + idempotencyKey。
5. 外部 MCP 不能伪造玩家 `/确认`。
6. 任何外部发送仍遵循 `SENT / FAILED_BEFORE_SEND / UNKNOWN`；UNKNOWN 不自动重发。
7. GM 推演秘书只读全量资料，输出只进 GM/MCP 会话。
8. 密钥、token、真实 QQ 标识不进入工作区、事件、日志或推送内容。
