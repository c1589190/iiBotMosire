# 玩家体验、交互与推演文档系统设计

> **状态**：提议（2026-10-24）。用户已明确目标与问题方向；具体规则待用户确认后升级为正式设计。
> **本文取代**：无。
> **关联设计**：D-010（私聊 + 公共群）、D-011（秘书子 Agent）、D-012（自然语言决策 + 硬确认）、D-014（秘书 cache / NapCat 历史）。
> **事实底稿**：[`../reports/2026-10-24-first-live-run-player-experience-audit.md`](../reports/2026-10-24-first-live-run-player-experience-audit.md)。

## 一、用户原话与要求

### 1.1 本轮问题原话（逐字）

> 「实际推演流程中也有大量真人推演不会犯的错误
> 例如推文的风格（大量掺杂程序状态）、反复确认（死磕条项目，打击玩家游玩积极性）、推文重点不明确、秘书Agent Markdown残留等，以及更加多的若干交互问题，这些你没有看到吗？难道这些就不是问题了吗？虽然不能通过程序解决，必须用额外的推演文档系统来解决」

### 1.2 本轮目标原话（逐字）

> 「把这些所有问题先都记录下来，然后你出解决方案，要求是让玩家的行动与信息获取变得轻松顺滑」

### 1.3 不可静默改变的用户既有裁定

- D-012 仍然有效：正式行动决策必须经过玩家硬确认；自然语言“同意/提交”不能替代确认。
- 本设计不取消硬确认，而是规定：
  - **只在正式行动草案终稿时确认一次**；
  - 报名、查询、查看信息、普通选择不进入硬确认；
  - 确认号必须与当前草案一一对应；
  - 已确认后不得再次索要确认；
  - 未确认草案不得 promote/package/commit。
- 若未来要允许“无确认自动执行”，那是新裁定，必须由用户明确追加 D-xxx，本文不默认采用。

## 二、目标与非目标

### 2.1 目标

1. 新玩家不看工作区、不懂 MCP、不懂修订号，也能在收到第一条私聊后知道：
   - 我是谁；
   - 我现在看到什么；
   - 我能做什么；
   - 我做完后会发生什么。
2. 玩家用自然语言表达行动，最多只需一次硬确认即可正式提交。
3. 玩家询问信息时，先得到直接答案，再得到最多 3 个可行动选项；不再被要求去读文件路径。
4. 所有玩家可见文本都必须像“世界内的人/秘书在说话”，不得像工程回执。
5. 公共推文只叙述世界事件与公开可感知变化，不展示程序状态、系统流程或模型内部信息。
6. 让“信息获取”从主动拉取（读工作区/查文件/读 ID）改为推送（开局卡/情境卡/结果卡/选项卡）。
7. 为人类推演者/Agent 提供一套可执行、可审稿、可复盘的推演文档系统，而不是继续堆提示词和 Skill。

### 2.2 非目标

- 不在本设计中改 P0–P8 的领域数据模型本身；
- 不新增公网 MCP、不降低身份、可见性或硬确认门槛；
- 不把自动监控变成自动生成剧情；
- 不用一个“万能提示词”替代文档、模板和审稿；
- 不在当前已被事故污染的 runtime 上做体验验收。

## 三、设计原则

按优先级排序：

### 原则 1：玩家只说人话，系统负责翻译

玩家输入自然语言。结构化、draftId、ticketId、revision、postId、workspace 路径等由系统/秘书/GM 处理，不进入玩家叙事文本。

### 原则 2：信息推给玩家，不让玩家拉文件

凡玩家做当前决策所需要的信息，必须在私聊正文中直接出现。工作区文件只是 Agent/GM 的持久化载体，不是玩家 UI。

### 原则 3：一条消息只讲一件事

- 一条消息只能有一个焦点；
- 公告、裁定、教程、流程说明不得和世界叙事混在同一段；
- 需要讲多件事时拆成多条，或使用固定分卡。

### 原则 4：确认只发生在不可逆的正式决策点

- 报名：填表/给信息即提交，不确认；
- 查询：直接回答，不确认；
- 普通对话/选项：不用确认；
- 正式行动：草案终稿时确认一次；
- 已提交：只回执，不再确认；
- 高风险行动仍是同一套一次确认，但草案必须显式写清代价与红线。

### 原则 5：先给事实，再给未知，最后给行动

任何结果反馈的结构固定为：

1. 已确认发生的事实；
2. 玩家新增知道的信息；
3. 玩家资源/关系/位置变化；
4. 仍未知或未决的事项；
5. 2–3 个下一步动作选项 + “也可直接说自己的做法”。

### 原则 6：后台状态永不入戏

以下内容只允许出现在 GM 私有记录、事件库、MCP 工具输出、开发日志：

- draftId/decisionId/ticketId/postId/revision/contentHash/turnId；
- PENDING_APPROVAL/APPROVED/PUBLISHED/COMMITTED/OPEN/CLAIMED；
- MCP/tool/schema/payload/prompt/token；
- workspace 路径、模块名、异常栈、模型名、API 名；
- “系统重启”“服务返回”“自动循环”“测试产物”。

唯一例外：玩家主动提问“这个功能怎么用/为什么没收到”时，系统可以用一条独立 `【系统】` 消息解释操作，但仍不得展示 ID、状态和文件路径。

### 原则 7：世界内声音分离

| 声音 | 谁在说 | 允许内容 | 禁止内容 |
|---|---|---|---|
| 秘书 | 玩家私人助理 | 第二人称、建议、整理、提醒、一次确认 | GM 裁定、后台状态、代码格式、越权承诺 |
| GM/推演 | 世界控制方 | 公开叙事、裁定结果、规则说明、系统公告 | 模型推理、工具日志、逐项程序状态 |
| 系统 | 宿主 | 发送失败、断线恢复、安全提示 | 冒充世界内角色、连续刷屏 |
| NPC | 世界内角色 | 台词、态度、行动 | 玩家系统信息、未来剧情机关 |

### 原则 8：默认成功路径短，异常路径可解释

- 默认：自然语言 → 一次确认 → 结果卡；
- 异常：一句话说明“发生了什么/你的进度是否保留/现在回复什么”；
- 禁止异常时输出异常类名、堆栈、完整工具结果或大段 schema 错误。

## 四、玩家体验主循环

### 4.1 进群/首次私聊

玩家首次接触 Bot 时，必须在**一条消息**内获得玩法卡：

```text
【玩法卡】
你是帕拉丁帝国西境的一名地方官/军官。现在不需要填长表，也不用看文件。
先告诉我三件事就可以开始：
1. 你想被怎么称呼；
2. 你想当什么身份（地方官/中央官员/军官，或你自己的设想）；
3. 你最想先玩哪一类事（政治/粮政/军事/司法/宗教/谍报）。

其余身份细节我和 GM 会先替你补成“暂定”，你随时可以改。
```

禁止首条消息出现：工作区路径、表单版本号、确认码、MCP、推文 ID、会议/报名流程说明。

### 4.2 报名

#### 4.2.1 最小必填

只要求玩家提供：

1. 称呼；
2. 身份方向；
3. 最想玩的内容方向。

其余字段由秘书根据世界设定生成**暂定值**，明确标注“可改”，不得阻塞提交。

#### 4.2.2 缺失项处理

- 玩家未提供的秘密/私人目标：留空或标明“玩家尚未指定”，不得编造；
- 资源、权限、职位、人际关系：秘书/GM 可合理暂定；
- 所有暂定项进入 GM 私有记录，不出现在玩家可见确认清单里；
- 报名状态变为 `SUBMITTED_PROVISIONAL`，立即进入审核；
- 不得要求“补齐后才能开始”。

#### 4.2.3 报名回执

只发一类短回执，不要求确认：

```text
已经记下了。你的暂定身份是：卡普亚北隘税关长，骑士，三十四岁。
我先按这个方向准备开局；你之后任意一句话都可以改。
```

禁止：

- “请阅读并确认角色卡”；
- “请打开 player/character-sheet.md”；
- “如需修改请重新填写报名表”；
- 老确认码、旧 form 版本号、QQ 后四位等历史残留流程。

### 4.3 开局信息包（开局卡）

报名审核后，正文直接包含：

```text
【开局卡｜<角色名>】
你现在在哪里：...
你面前正在发生：...
你知道的三件事：
1. ...
2. ...
3. ...
你手里有：...
你的限制：...
你现在可以：
A. ...
B. ...
C. ...
也可以直接说你自己的做法。
```

要求：

- 不超过一屏；如果细节很多，仅给“现在需要知道的”，其余玩家问再答；
- 不出现 `player/`、`gm/`、`notes/` 或任何路径；
- 不要求玩家“先阅读文件再开始”；
- 至少提供 2–3 个有意义的可行动选项；
- 选项必须体现不同路线和代价，不得只是换皮。

### 4.4 信息查询

当玩家问“现在什么情况/我能做什么/我有哪些权限”：

1. 先用 1–3 句直接回答；
2. 再给最多 3 条与当前问题相关的可行动选项；
3. 不要先列工作区、文件、版本和后端状态；
4. 不知道怎么答时，明确说“这一点我暂时不能确认”，并给出下一步可以问谁/做什么；不得编造。

响应长度建议：

- 普通信息答复：≤ 6 行；
- 需要解释规则：≤ 10 行，并按“现在能用/现在不能用/下一步”三段；
- 玩家要求“展开”时才发详细内容。

### 4.5 行动

#### 4.5.1 理解与草案

收到自然语言行动后，秘书先完成内部结构化，再向玩家发**一份**草案。草案格式：

```text
我理解你要：
你在<地点>，以<身份>，做<动作>，目标是<目标>。

执行方式：
1. ...
2. ...
3. ...

风险/代价：
...

如果按此执行，请回复：
/确认 <短确认码>

只会确认这一次；你回复“改”可以调整。
```

硬确认仍符合 D-012，但缩短为单一动作块。

#### 4.5.2 短确认码

- 玩家侧只显示一个短确认码（如 `K7Q2`），不显示 revision/contentHash/postId；
- 短码由宿主映射到当前 draftId，一次性、可过期、不可复用；
- 若实现暂不引入短码，则全 draftId 只能出现在这一行确认命令中，其他任何消息不得出现；
- 确认命令格式固定、可复制，避免玩家自己猜；
- 草案被修改后旧码立即失效，并明确告知“旧确认码作废，新草案确认码为...”，但此提示只出现一次。

#### 4.5.3 确认策略

| 动作类型 | 是否需要玩家硬确认 | 规则 |
|---|---|---|
| 报名/提供信息 | 否 | 提供即提交，缺失项暂定 |
| 普通信息查询 | 否 | 直接回答 |
| 查看状态/工作区 | 否 | 秘书直接转述，不给路径 |
| 普通行动 | 是，最多一次 | 草案终稿后一次确认 |
| 高风险不可逆行动 | 是，最多一次 | 草案必须写清代价与不可逆点 |
| 已提交/已确认行动 | 否 | 只发回执，不得再问 |
| 玩家主动改口 | 是，最多一次 | 生成替代草案，旧草案作废，不重复确认旧版 |

#### 4.5.4 行动回执

确认后只发：

```text
已记录。你在本旬的行动是：...
GM 裁定后，我会把结果和你能继续做的事一起告诉你。
```

不再出现：工单号、postId、ticket status、revision、审批链。

### 4.6 结果反馈

正式反馈必须按结果卡输出：

```text
【本旬结果｜<地点/日期>】

已经发生：
...

你知道了什么：
...

你的变化：
- 资源/位置/关系：...

仍未确定：
...

下一步你可以：
A. ...
B. ...
C. ...
（也可以直接说自己的做法。）
```

硬性规则：

- “已经发生”必须是具体事实，不得用“可能/待定/建议”填满；
- 不允许只写“未发生任何世界变化”作为玩家结果；若确实 no-op，应说明为什么以及玩家下一步如何修正；
- 不展示模型推理过程、tokens、工具调用、内部评分；
- 不重复整段结果；同一结果只发一次；
- 一回合只保留一份正式结果卡；公共与私密分别发，但不得重复同质内容。

### 4.7 断线/错误恢复

错误卡只包含三件事：

```text
【系统】
刚才消息没有正常送达/处理。你已提交的<行动/报名>仍然保留/未保留。
请直接回复：<一个动作>。
```

禁止：

- 异常栈、类名、HTTP code、schema 原文；
- 把系统错误写成 GM 裁定；
- 重复发送同一条结果；
- 自动重试导致刷屏。

### 4.8 公共群与私聊

- 私聊：玩家行动主通道、秘书对话、私密结果、个人信息；
- 公共群：公开叙事、世界状态变化、招募/公开规则；只发世界内内容；
- 公共群固定一条“玩法卡/如何开始”，不反复刷；
- 自动日推只在世界时间真正推进且由 GM 审核后发布；
- 任何“自动监控/测试/系统说明”不得作为公开叙事发布。

## 五、玩家可见文本规范

本规范适用于秘书私聊、GM 公开推文、私密结果、报名回执、错误提示。

### 5.1 格式

必须：

- 使用纯文本段落；
- 列表最多 5 项；
- 每条消息只讲一个焦点；
- 标题只用中文方括号（如 `【本旬结果】`），不使用 Markdown 标题；
- 选项用 A/B/C 或 1/2/3，保留玩家自由输入。

禁止：

- `##`、`**`、表格、``` 代码块、`>` 引用；
- 反引号包裹 ID、路径、命令；
- JSON、YAML、SQL、堆栈、schema 片段；
- 长段落堆叠多个主题；
- “第一回合/第 2 日/程序状态”替代世界内日期和地点。

### 5.2 长度

建议上限，超出时拆成“先看这些/需要展开再说”：

| 内容类型 | 建议上限 |
|---|---:|
| 普通秘书回复 | 6 行 |
| 信息卡/开局卡/结果卡 | 一屏，约 350–500 中文字 |
| 公共推文 | 4 段，约 300–500 中文字 |
| 选项 | 2–3 个 |
| 错误卡 | 3 行 |

### 5.3 术语

玩家可见文本不得使用：

```text
draftId decisionId ticketId postId revision contentHash turnId
MCP tool schema payload prompt token API
PENDING_APPROVAL APPROVED PUBLISHED COMMITTED OPEN CLAIMED
workspace path markdown ``` `player/...`
```

### 5.4 事实与不确定性

- 先写“已经发生”的事实；
- 再写“你新增知道”的信息；
- 再写“未知/未决”；
- 每条不确定性必须有清楚边界，不能整段都是“可能”；
- NPC 态度与结果不得用“系统拒绝”代替，必须给世界内原因或明确 GM 待定说明。

### 5.5 禁止的自动化语言

- “这是自动监控/发布链路的测试产物”；
- “不代表世界时间已经推进”；
- “系统说明”；
- “真实模拟/联调/环境/链路”；
- “候选/兜底/待确认/draftId”。

如果必须向玩家解释技术问题，用独立系统消息，且先确认玩家是在问操作问题。

## 六、额外推演文档系统

本设计的核心不是再写一个万能 Skill，而是建立**玩家体验文档包**。每份文档有唯一职责，秘书/GM 提示词引用它们，发布前按它们审稿。

建议目录（逻辑名，最终落点由实现时确定）：

```text
simulation/player-experience/
  00-experience-charter.md
  01-player-visible-style.md
  02-secretary-playbook.md
  03-confirmation-and-recovery.md
  04-information-cards.md
  05-publication-templates.md
  06-editorial-checklist.md
  07-automation-boundaries.md
  08-bad-good-examples.md
  09-playtest-and-acceptance.md
```

### 6.1 各文档职责

| 文件 | 必须回答的问题 |
|---|---|
| `00-experience-charter.md` | 玩家为什么来玩、什么样的体验算成功、哪些底线不可违反 |
| `01-player-visible-style.md` | 什么能说、什么不能说、长度、格式、视角、语气 |
| `02-secretary-playbook.md` | 秘书如何接待、询问、整理、提交、陪伴玩家；何时该闭嘴 |
| `03-confirmation-and-recovery.md` | 唯一确认点、确认码有效期、改口、重复/断线/上下文丢失 |
| `04-information-cards.md` | 玩法卡、开局卡、情境卡、结果卡、错误卡的固定结构 |
| `05-publication-templates.md` | 公开推文/私密结果/公告/招募/回合反馈模板与正反例 |
| `06-editorial-checklist.md` | 发布前逐条审稿，不通过就不发 |
| `07-automation-boundaries.md` | 监控能做什么、绝对不能做什么、停机与熔断 |
| `08-bad-good-examples.md` | 本轮真实坏例、原因、可复制的好例 |
| `09-playtest-and-acceptance.md` | 如何用真人/模拟玩家验收“轻松顺滑” |

### 6.2 文档权威顺序

1. 用户当次明确指令；
2. 项目设计裁定（含 D-012）；
3. 本文；
4. `simulation/player-experience/00–09`；
5. 秘书/GM 提示词与 Skill；
6. 旧模板、旧 notes、旧工作区文件。

任何秘书/GM 提示词与玩家体验文档冲突，以后者为准；旧版本必须标 `DEPRECATED`，不能继续被 Agent 读取为有效规则。

### 6.3 文档生命周期

- 每次真实推演后更新 `08-bad-good-examples.md`；
- 每次发生风格/确认/信息问题，先补 checklist 或模板，不先改程序；
- 每个新战役只覆盖世界观与语气，不复制交互规则；
- 文档版本必须可被秘书工作区 `AGENTS.md`/共享 Skill 引用（版本号 + hash）；system prompt 保持最小；
- 旧版本归档，不保留 `start-here-v2/v3` 这类需要玩家自行判断的路径。

## 七、秘书行为规则（摘要）

秘书是“玩家的私人助理”，不是 GM，不是系统日志，不是规则裁判。

必须：

1. 先说“我理解你的目标”，再给一个可行方案；
2. 给不超过 3 个选项，并允许自由输入；
3. 玩家说“随便你/你决定”时，秘书可以按最合理路线暂定并明确一句，不得继续索要无必要细节；
4. 玩家已提供的信息不得重复询问；
5. 玩家表示看不到文件时，直接把文件要点转成聊天正文；
6. 信息不足时，只问一个最影响行动的问题；
7. 已提交后不得重复要求确认；
8. 只显示一个与当前草案对应的确认命令；
9. 提交失败/卡住时，先说明玩家输入是否保留，再给下一步；
10. 绝不把工具错误、模型名、workspace 路径、事件 ID 发给玩家。

禁止：

- 让玩家阅读工作区文件；
- 列版本差异；
- 用 Markdown 表格/代码块/标题；
- 输出“消息已收到，请稍候”后无后续；
- 连续确认/反复确认；
- 把秘书自己的裁定说成 GM 裁定；
- 自行决定战斗胜负、税收、伤亡、外交结果；
- 在玩家未授权时公开其秘密/私人目标。

## 八、GM/推演者行为规则（摘要）

GM 负责“世界如何回应行动”，不应把内部工作流当剧情。

每次发布前问：

1. 这条写的是世界内发生了什么，还是我们系统做了什么？
2. 玩家能不能看出谁、在哪、发生了什么变化？
3. 有没有一条清楚的下一步？
4. 有没有泄露私密、程序信息或模型推理？
5. 是不是把多个主题塞进一条？
6. 是否存在“可能/待定”淹没“已发生”？
7. 是否重复了上一条结果？

公开推文结构：

```text
【地点｜日期】
一个具体场景/事件
一个公开可感知的后果
一个下一步钩子
```

不允许公开推文写：

- “系统刚刚没有……”
- “自动监控/测试产物”
- “世界时间没有推进”
- “MCP/工具/schema”
- “请确认/阅读文件”
- 大段规则说明；规则说明另行以 GM 公告发布。

## 九、自动化边界

### 9.1 允许

- 只读轮询工单/推文状态；
- 检测新工单并通知 GM；
- 在明确授权下，发布已经人工/GM 生成并审核的待审帖；
- 记录事件、PID、心跳、lastError；
- 对已存在的失败送达做一次不重复的显式处理。

### 9.2 禁止

- 自动生成新剧情/新日推；
- 自动推进 campaign clock；
- 自动创建“第 X 回合·第 X 日”；
- 自动批准或发布自己生成的内容；
- 自动修改世界事实；
- 以“5 秒轮询”为由连续发送；
- 失败后无限重试/轰炸。

### 9.3 硬限制

- 同一 post 只发一次；失败后需显式授权重试；
- 单次自动循环最多处理已有待审项；没有新内容就什么都不做；
- 每 5 秒只做只读采样，不产生可见内容；
- 出现 `FAILED`/`UNKNOWN` 立即停发并报告；
- 操作者在启动自动循环时必须选择“观察模式/发布已有草稿模式”，默认观察；
- 必须有一键停止和明确 PID/状态文件。

## 十、发布前审稿门

每一份玩家可见文本都必须过 `06-editorial-checklist.md`。至少包含：

- [ ] 是否含程序状态、ID、路径、版本、内部术语？
- [ ] 是否有 Markdown 标题/表格/代码块/反引号？
- [ ] 是否只讲一个焦点？
- [ ] 玩家是否能在 10 秒内知道“发生了什么/我能做什么”？
- [ ] 是否有具体事实，而不是整段“可能/待定”？
- [ ] 是否重复要求确认或重复发送？
- [ ] 是否把系统/GM/秘书/NPC 口吻混用？
- [ ] 是否泄露私密信息或模型推理？
- [ ] 是否给出了 2–3 个可行动选项？
- [ ] 如果玩家问“我该怎么办”，这条能否直接回答？

任何一项不通过：不发，回退给写作者重写。代码门禁只能检查部分机械项，内容和语气必须由编辑审稿。

## 十一、验收标准

### 11.1 玩家体验验收

使用干净 runtime / 干净测试角色，至少 5 名未读过设计文档的测试玩家，只看第一条私聊和公共群 pinned 玩法卡：

1. 90% 玩家能在 1 条消息内说出“我现在能做什么”；
2. 首次行动从意图到提交 ≤ 2 条玩家消息（自然语言 + 一次确认）；
3. 没有任何玩家需要询问“怎么填/怎么使用/@ 还是私聊/文件在哪”；
4. 所有玩家可见消息中：
   - 程序 ID 出现次数 = 0（除唯一一次确认命令）；
   - Markdown 标记出现次数 = 0；
   - 代码块/文件路径 = 0；
   - 同一结果重复 = 0；
5. 每条结果卡都包含“已发生/你知道了什么/下一步”；
6. 玩家能在结果后直接选择 A/B/C 或自由输入，不需要再问“然后呢”；
7. 确认只出现一次；不出现“已提交后再次确认”；
8. 失败/重启后玩家能明确知道自己的行动是否保留。

### 11.2 推演文档验收

- 10 份文档全部存在、有唯一 owner、有版本号；
- 秘书通过工作区 `AGENTS.md`/共享 Skill 引用同一套玩家体验文档；GM prompt 引用发布审稿规则；
- 至少 2 名审查者用 `06-editorial-checklist.md` 抽查发布内容；
- 每轮真实推演后都至少新增 1 条坏例与 1 条好例到 `08-bad-good-examples.md`；
- 自动监控脚本通过“只读模式”测试，确认不产生新内容。

## 十二、实施顺序（建议）

1. **先写文档**：建立 `simulation/player-experience/` 十份文档，先解决“怎么写/怎么审”。
2. **改秘书与 GM 提示词**：让它们引用文档而不是内嵌互相冲突的规则。
3. **改玩家入口**：首条私聊推送玩法卡；报名最少三项；取消文件路径和长表。
4. **改确认链路**：一次确认；短确认码或唯一确认行；取消报名确认；修复“已提交又要求确认”。
5. **改信息呈现**：开局卡/情境卡/结果卡/错误卡固定模板；秘书/GM 输出格式统一。
6. **改发布门禁**：增加审稿 checklist；自动化脚本只读化。
7. **清理旧版本**：所有 v1/v2 文件归档并标注 deprecated；玩家工作区只保留 current。
8. **干净 runtime 复盘**：按 §11 做 5 人 playtest；未过验收不进入下一轮正式推演。

## 十三、代码与文档的分工

| 问题 | 主要解决层 |
|---|---|
| 玩家看不到行动是否被记录 | 代码/持久化 + 游戏状态 |
| 文件路径、ID、Markdown 出现在文本 | 代码格式化/输出边界 + 文档规范 + 审稿 |
| 反复确认、已提交又确认 | 状态机/确认协议 + 文档规则 |
| 推文没有重点、语气像日志 | 推演文档 + 模板 + 编辑审稿 |
| 信息难获取 | 玩家信息卡设计 + 秘书行为 + 前端/推送 |
| 自动化刷屏 | 代码熔断 + 自动化边界文档 + 明确操作权限 |
| 秘书忘上下文、卡死 | 代码 Session/cache/状态 |
| 世界事实与角色冲突 | canonical 领域状态 + GM 流程文档 |

**结论**：代码解决“不能错/不能丢/不能越权”，文档解决“怎么像人玩、怎么让玩家不累”。两者都不能缺。

## 十四、本轮不做什么

- 不改当前正在运行的 app；
- 不覆盖 `simulation/dist` 旧 jar；
- 不删除事件库或群消息；
- 不自动发送任何 QQ 消息；
- 不把本提议当作已获用户确认的最终规则。
