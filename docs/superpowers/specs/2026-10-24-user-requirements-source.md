## 二、需求拆分

### D-001 QQ 接入与可替换 Adapter

- **用户原话依据**：「把QQ账号接入Bot框架」「QQ对接协议暂时使用Napcat，要求Adapter可封装」。
- **设计含义**：
  - 首期实现 NapCat / OneBot 11 Adapter；
  - 领域层只依赖 `MessagingAdapter` 端口；
  - OneBot JSON、连接方式、鉴权、重连、消息分段、`echo` 等只在适配器模块；
  - 将来可替换为其他协议而不改回合/Agent 逻辑。
- **状态**：有效。

### D-002 QQ 用户角色：玩家 / 推演

- **用户原话依据**：「指定QQ账号用户为“玩家”、“推演”」。
- **设计含义**：
  - 角色由服务端配置（QQ 号 → 角色）决定；
  - 非登记用户默认拒绝或仅安全提示，不能自行注册为玩家/推演；
  - 角色决定命令面、可见信息面和 Agent 上下文，不能由聊天文本提升；
  - “推演”是中央 Agent 的人类操作/设定角色，不等同于系统管理员。
- **状态**：有效。

### D-003 固定提示词与世界观设定载入

- **用户原话依据**：「围绕固定提示词构建世界观设定，将玩家/推演提供的设定载入」。
- **设计含义**：
  - 固定系统提示词是版本化核心，不得被普通聊天静默改写；
  - 世界设定可来自玩家/推演，但必须经过提案、校验、冲突检查、批准、版本化后才能进入全局世界观；
  - 每个回合/每次核心 Agent 调用要记录 world version 与 prompt version/hash；
  - 已启用设定是可追溯事实，不覆盖历史版本。
- **状态**：有效。

### D-004 自由对话 + 回合循环 + 格式化决策

- **用户原话依据**：「实现回合循环，让QQBot可自由与玩家交流可以交流的世界内情况，然后允许玩家格式化提交决策」。
- **设计含义**：
  - 每个玩家可与 Bot 在自己可见的世界信息范围内进行多轮交流；
  - 有明确的回合开启、决策提交、冻结、推演、发布、下一回合状态；
  - 玩家决策使用固定格式；提交解析、校验、确认与截止时间为宿主逻辑，不完全依赖 LLM 自由解释；
  - “可以交流的世界内情况”要求按玩家可见性过滤，而非仅靠礼貌提示。
- **状态**：有效；具体格式待用户裁定（见需求基线 §7）。

### D-005 中央 Agent 审核与推演

- **用户原话依据**：「提交决策后，由中央Agent审核、推演各个玩家的决策，出信息」。
- **设计含义**：
  - 中央 Agent 接收冻结回合的全部玩家决策与世界快照；
  - 先做结构化/规则审核，再由模型推演冲突与后果；
  - 输出必须为可校验提案，不能由模型直接写数据库；
  - 结果既要给公开信息，也要给各玩家的私密信息，且按可见性发布；
  - 失败时进入可观测失败态，不允许半提交。
- **状态**：有效；是否要求推演人工签核待用户裁定。

### D-006 Java + Maven

- **用户原话依据**：「编程语言选择 java+maven」。
- **设计含义**：Java 21、Maven 多模块、父 POM 管理版本；具体 Wrapper 版本和门禁在 P0 落地。
- **状态**：有效。

### D-007 优先复用 ProjectMosire 三库

- **用户原话依据**：「Agent实现优先使用隔壁的ProjectMosire里三大库」。
- **按发布页口径的解释（待用户确认是否正是此意）**：
  - `io.mosire:agentlib-mosire:0.2.3`
  - `io.mosire:workspace-mosire:0.2.3`
  - `io.mosire:docs-mosire:0.2.3`
- **设计含义**：
  - 优先复用其中的 LLM 客户端、AgentLoop、工具注册/授权、事件存储、MCP 服务、Workspace 挂载、Docs 文档能力；
  - 不复制一套平行的 LLM/工具/存储框架；
  - 第一版优先使用三库的固定发布版而非 SNAPSHOT；
  - 若需 Brain/Main 中的能力，先证明三库无法满足，再另行裁定。
- **状态**：原话有效；“三大库 = 上述三件”是调研解释，等待用户确认。

### D-008 对外 MCP 总控

- **用户原话依据**：「也许还可以做一个对外MCP工具来方便外部Agent（如你，DSH）总控事件流，保证不出岔子」。
- **设计含义**：
  - “也许”表示增强项，不应阻塞 QQ + 回合核心 P0；
  - 外部 MCP 是一等安全边界，不提供关机/任意 QQ 发送/伪造玩家决策/直接改世界等能力；
  - 所有写操作必须过回合状态机、期望版本与幂等键检查；
  - 默认只绑回环地址、默认关闭，需用户显式启用；
  - 外部 Agent 可以观察事件流、检查健康/不变量，并在受控范围内推进回合。
- **状态**：方向有效；写工具集合与鉴权方式待用户裁定。

### 5.2 D 编号拆分

#### D-010 私聊 + 公共群

- **含义**：每个玩家与 Bot 有独立私聊；另设公共群作为公开信息/公告通道。
- **v1 建议边界**：公共群默认只由 Bot/推演发布公开信息，不把群内普通聊天接入玩家 Agent；如要群内玩法，另立设计。
- **状态**：用户已选方向；群内是否允许玩家聊天待 Q8 细化。

#### D-011 每玩家一个秘书子 Agent

- **含义**：
  - 每个玩家有独立“秘书”子 Agent，与玩家私聊；
  - 秘书可与 GM（中央推演 Agent/推演角色）交流；
  - GM 向秘书提供**已经审查和过滤**的信息，秘书不应直接读取完整世界数据库；
  - 秘书基于玩家交流形成决策，通过工具提交；
  - 玩家必须用**硬性命令**确认后，决策才真正进入回合。
- **状态**：有效方向；秘书与 GM 的协议、信息分级、硬确认命令形式待细化设计。

#### D-012 自然语言决策 + 工具结构化 + 硬确认

- **含义**：
  - 玩家用自然语言与秘书讨论；
  - 秘书用工具生成结构化 `DecisionDraft` 并回显；
  - 秘书不能直接提交有效决策；
  - 玩家用固定硬命令（例如 `/确认 <draftId>`）确认，宿主校验后才写入回合；
  - 自然语言“同意/提交”不算硬确认。
- **状态**：有效；精确命令与草稿过期规则待实现设计确认。

#### D-013 外部 MCP 全功能总控

- **含义**：
  - 外部 Agent 应能通过 MCP 完成**游戏事件流控制面**的全部操作，而不仅是只读监控；
  - 仍必须保留身份、状态机、幂等、审计与玩家硬确认等宿主不变量；
  - 不把“全功能”解释为允许绕过玩家确认、伪造决策、关机或读取密钥。
- **状态**：有效方向；具体工具清单与“非游戏运维操作”边界待确认。

### 5.3 补充裁定（2026-10-24，会话 cache 与 NapCat 历史）

#### D-014 秘书会话 cache、cache 切换与只读 QQ 历史

- **用户原话（逐字）**：
  > 「1 我认为直接做一个对接Napcat的通用聊天记录查看器最方便
  > 2 允许单个秘书位置切换不同id的cache即可
  > 3 允许当前秘书方便阅读同秘书之前的Cache即可
  > 4 GM自然能用查看秘书上下文的工具
  > 5 迎刃而解」
- **设计含义**：
  - App 侧保存可恢复的秘书 `ContextWindow` cache，不能把内存窗口当作唯一历史；
  - 同一秘书槽位可在同一玩家的多个 cacheId 之间切换，旧 cache 不删除；
  - 秘书可读取同一玩家以前的 cache；GM/外部 supervisor 可读取并切换任意已注册玩家的 cache；
  - NapCat 聊天记录作为只读外部查看器，用于人工恢复/证据查看，不冒充 LLM 上下文；
  - 不提供跨玩家 cache 借用，不把 NapCat 历史自动注入模型。
- **当前正本**：[`2026-10-24-secretary-conversation-cache-and-qq-history.md`](2026-10-24-secretary-conversation-cache-and-qq-history.md)。
- **状态**：有效；实现进行中。

### 5.4 补充裁定（2026-10-24，玩家体验与推演文档系统）

#### D-015 玩家行动与信息获取必须轻松顺滑

- **用户原话（逐字）**：
  > 「实际推演流程中也有大量真人推演不会犯的错误
  > 例如推文的风格（大量掺杂程序状态）、反复确认（死磕条项目，打击玩家游玩积极性）、推文重点不明确、秘书Agent Markdown残留等，以及更加多的若干交互问题，这些你没有看到吗？难道这些就不是问题了吗？虽然不能通过程序解决，必须用额外的推演文档系统来解决」
  >
  > 「把这些所有问题先都记录下来，然后你出解决方案，要求是让玩家的行动与信息获取变得轻松顺滑」
- **设计含义**：
  - 玩家可见文本必须去工程化：不得出现程序状态、ID/路径/Markdown 残留、系统/测试口吻；
  - 一条消息只讲一个焦点，先给具体事实，再给未知，再给 2–3 个可行动选项；
  - 信息必须推给玩家，不得要求玩家阅读工作区文件或自行理解版本；
  - 报名、查询和普通交流不得因缺项或审批状态反复阻塞；
  - D-012 的正式行动硬确认保留，但必须只在草案终稿处出现一次，不得反复确认或因 ticketId/draftId 混淆形成死胡同；
  - 必须建立独立的推演文档系统，包含玩家可见文风、秘书行为、确认与恢复、信息卡、推文模板、发布前审稿清单、自动化边界、正反例与验收。
- **问题与方案正本**：

### 5.6 补充裁定（2026-10-24，平台级 QQ 能力与自主入团）

#### D-017 connectlib 平台级 QQ 能力与受控自主入团

- **用户原话（逐字）**：
  > 「此外需求还有，MCP读取群聊之后，可能有公屏玩家想直接加入，应当允许Agent自主把这名玩家加入游戏，并自主发送报名表，这个能实现吗？裁定你自己先做一遍，我认为应该直接扩大到平台量级，做成connectlib的全局最高权限工具，然后通过限制权限来限制执行」
- **裁定**：
  1. **方向采纳**：`iibot-connect` 提供平台级 QQ 能力，作为全局最高权限的 typed capability port：
     读取 Bot 可访问的私聊/群历史、最近会话、群列表、群成员、消息定位，以及发送私聊/群消息。
     不提供 raw OneBot action、任意 JSON、任意数据库或任意 shell 的执行口。
  2. **“平台量级”边界**：只能是 Bot 账号 / NapCat 当前可访问的会话与群；不能读取两个其他用户之间的私聊，
     也不能读取 Bot 未加入的群。承载能力不等于突破 QQ 平台权限。
  3. **权限分层**：connectlib 只实现能力，不决定游戏权限；对外暴露由 app/MCP 的
     `ToolCallAuthorizer` 控制。权限至少覆盖 role/allowlist、operation scope、target scope、
     rate/quota、idempotency 和 audit。默认只开放读取与当前推演群；任意发送、任意群入团必须显式配置
     allowlist 或 `*` 后才启用。
  4. **公屏自主入团**：允许外部控制方 Agent 根据群消息自主调用高层 onboarding 工具，完成
     注册玩家、创建秘书、发送报名表，不要求再由 app 内 Agent 审核，也不要求逐次真人确认；
     用来源证据与权限策略替代逐次确认。调用必须带
     `sourceGroupId` / `sourceMessageId` / `qqId` 作为证据，由宿主校验消息真实存在且发送者匹配；
     默认要求报名/加入类 opt-in 文案，默认只允许当前推演群，支持配置放宽。
  5. **安全限制**：不能一次调用批量抓取或群发；单玩家幂等；单 QQ 只注册一次；报名表发送走
     delivery ledger，`UNKNOWN` 不自动重发；日志不记录正文、token 或完整协议数据。
     该自主入团例外只覆盖“校验通过的报名响应”，不自动扩大到任意群发或任意公告。
- **正本**：[`../plans/2026-10-24-mcp-external-authoring-and-qq-chat-access-plan.md`](../plans/2026-10-24-mcp-external-authoring-and-qq-chat-access-plan.md)
- **状态**：已实现代码与自动化测试；未部署 simulation jar、未做真实 NapCat/QQ smoke。

### 5.7 补充裁定（2026-10-24，工单板等待模式）

#### D-018 工单板长轮询等待

- **用户原话（逐字）**：
  > 「别急，再加一个新功能，那就是给Agent看的那个告示板加一个等待，如果处于等待模式，那么在第一条信息来临前，这个工具的调用不会结束」
- **裁定**：
  - `tf_ticket_board` 增加 `wait=true` 与 `waitSeconds`；
  - 已有 OPEN/CLAIMED/CONFIRMED 工单时立即返回；
  - 没有待处理工单时，调用阻塞到下一次成功工单变更/新工单到达，或 `waitSeconds` 超时；
  - 默认等待 300 秒，上限 1800 秒；超时返回 `waitTimedOut=true` 和当前板面，Agent 可再次调用；
  - 只有成功提交的工单变更才唤醒；存储失败不唤醒；
  - 等待是宿主内部 condition 通知，不要求外部 Agent 轮询 MCP；
  - 超时/中断不等于自动处理工单，Agent 仍需按工单流程操作。
- **状态**：已实现代码与自动化测试；未部署、未做真实 DSH 长等待 smoke。

### 5.8 补充裁定（2026-10-24，出站消息节奏）

#### D-019 所有外发逻辑消息必须有最小间隔

- **用户原话（逐字）**：
  > 「哦对了还有，发任何消息都不能挤着发，例如确认私信已经收到的消息，就需要自动延迟个100ms~200ms」
- **裁定**：
  - 所有经宿主统一外发出口的逻辑消息共享一个全局节奏锁；
  - 默认最小间隔 150ms，生产配置范围 100..200ms；
  - ACK 与正式回复来自不同线程，也必须共用同一节奏，不得并发挤发；
  - 公开推文、私密推文、回合结果、投诉回应、自主入团报名卡等所有出站路径统一生效；
  - 节奏等待发生在外部请求发出前；被中断时返回发送前失败，不伪装成已发送；
  - 不依赖 MCP/DSH 侧手工 sleep，宿主自动执行。
- **状态**：已实现代码与自动化测试；运行中的旧 jar 未替换。
