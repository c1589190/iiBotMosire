## 三、结论摘要

首轮并非“核心链路完全不可用”。真实 1:1 私聊、群发、MCP、行动池、裁定包、批次、推文审核与发布都实际出站过。然而：

1. **工程可靠性问题**让开本和状态推进多次中断；
2. **领域状态语义问题**让行动“未确认却提交”、no-op 却 `COMMITTED`、回合仍 OPEN 却已发回合反馈；
3. **玩家体验层问题**让玩家看不懂、反复确认、不知道自己能干什么，且被工程术语和 Markdown 噪声包围；
4. **自动化治理问题**让一个本应只观察的 5 秒脚本变成自动生成日推、自动推进时间和自动群发的机器。

其中第 3 类问题不能只靠代码修复。即便所有状态机都正确，如果秘书和推演者继续说工程话、发 Markdown、死磕确认，玩家仍然不会觉得这是一个能玩的推演。

## 五、问题链：为什么玩家体验会烂

1. **后台状态没有边界** → 所有 ID、状态、路径都直接进玩家文本；
2. **秘书把“严谨”理解为“逐项确认”** → 表单缺项、确认码、draftId、ticketId 反复阻塞；
3. **信息以文件为中心，不以玩家当前场景为中心** → 让玩家读工作区，而不是推一张“现在你知道什么/能做什么”卡；
4. **GM 把世界状态写成系统变更日志** → 推文没有角色、地点、后果和钩子；
5. **自动化只被要求“每 5 秒做什么”，没有被要求“永远不做什么”** → 监控变成内容机器；
6. **没有发布前编辑审稿** → 程序成功即视为体验成功；
7. **没有 canonical 玩家状态** → 报名、角色、行动、回合、信息获取不能形成连续体验。

## 六、不是问题或需区分的点

- 保留 `/确认 <draftId>` 本身不是错误：D-012 要求对正式决策做玩家硬确认。错误是**确认出现多次、出现时机错误、把报名/查询也当决策**。
- 群内公开叙事本身不是错误；错误是把公开群当后台日志和系统状态显示屏。
- `可能/待定` 有时必须存在；错误是整篇反馈都是可能/待定，而没有先给已确认事实。
- 报名可以缺失项；错误是缺失项阻塞提交，以及让玩家承担秘书/GM 的整理工作。
- 自动监控本身有价值；错误是监控进程调用内容生成和发布工具。
