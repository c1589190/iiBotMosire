# docs/superpowers —— 项目设计目录索引

> **本目录属于项目设计，不属于项目维护。**
> 收代码/架构/数据/接口/工具面/载荷/运行时阶段/提示词与可见性语义。
> 维护规则（文档系统、Skill、门禁、协作、环境）去 [`../agents/`](../agents/AGENTS.md)；实时状态只看 [`../agents/STATUS.md`](../agents/STATUS.md)。

## 一、目录职责

| 目录/文件 | 放什么 | 什么时候读 |
|---|---|---|
| `specs/2026-10-24-user-requirements-source.md` | **用户需求原话 + D-xxx 拆分** | 任何设计/实现前先查 |
| `DESIGN_RULINGS.md` | 设计裁定索引；不复制正文 | 找“用户到底怎么定过”时 |
| `specs/**` | 专题设计、契约、目标运行序列、模块边界、数据形状、验收判据 | 设计/派单/实现前 |
| `plans/**` | 进行中的实现计划；不是设计本身 | 派单/执行前 |
| `reports/**` | 调查、审计、复现、证据报告 | 追溯事实/评审时 |
| `reviews/**` | 独立评审与裁决 | 评审/关账时 |
| `status/**` | **历史状态快照**；不是当前状态入口 | 只作追溯 |
| `../archive/legacy-game/**` | 已退出的文游历史设计/计划/状态/报告 | 只作追溯，禁止作为当前依据 |

## 二、设计文档规则

1. 用户代码/设计裁定逐字写进需求原稿或对应 spec，保留日期与来源；不写进维护裁定。
2. 设计文档必须区分：
   - 用户原话/裁定；
   - 现状事实（`file:line` 或 URL）；
   - 目标运行序列（阶段、顺序、读写、数据所有权、失败、日志、测试锚点）；
   - 子设计嵌入点与对父序列的影响；
   - 验收判据与负向用例；
   - 未定项/blocker。
3. 小改：原地改目标运行序列/形状/公式，并在文末「修订记录」写原文、原因、用户原话与日期。
4. 大改（阶段顺序、数据所有权、跨模块契约、多个责任区、世界语义变化）：新建文档，双方加 `本文取代/取代者` 头。
5. 不得按文件名日期推断有效性；以正文状态头、用户原话日期、代码/测试为准。
6. 旧设计不删、不篡改；只加状态/取代头。
7. 不用 `@` 导入长文；用相对 Markdown 链接。
8. 旧文游文档统一归档到 `docs/archive/legacy-game/`，不参与当前文档链接门禁；当前导航不得重新指向归档文件。

## 三、新文档命名与状态头

建议命名：`YYYY-MM-DD-<主题>.md`。

每个设计文档标题下至少写：

```markdown
> **状态**：有效 / 提议 / 历史 / 被取代（YYYY-MM-DD）
> **取代者**：<路径>（仅被取代时）
> **本文取代**：<路径>（仅取代旧文时）
> **用户原话**：<逐字或指向原稿条目>
```

## 四、设计裁定的查法

1. 先查 `DESIGN_RULINGS.md` 有没有主题索引；
2. 再查 `specs/2026-10-24-user-requirements-source.md` 的 D-xxx；
3. 再按主题查 `specs/**` 的文件头/取代关系；
4. 最后回代码/实际运行核机制性描述，不要照旧台账猜。

已有裁定不得重复问用户；确实无裁定时，按 [`../agents/WORKFLOW.md`](../agents/WORKFLOW.md) 的溯源要求提带出处的问题。
